**Written for:** the project owner, the supervisor and the Main Controller.

**Status:** declared on 12 November 2026 (UTC), **before** any formal data and **before** the reserved TEST runs are opened.

**Why it exists.** The supervisor's condition (11 November 2026): "Before opening the reserved TEST data, please ensure the measurement scripts and experiment matrix are finalized and checksummed as planned. **What it binds.** Everything below is pinned by SHA-256 in `configs/formal/AZTA-EXP-v1_formal_addendum_manifest.json`. That manifest names the frozen release manifest (`configs/exp_v1/AZTA-EXP-v1_freeze_manifest.json`, `221884e0…3b5516`). `rehearsal_tools/exp_addendum.py verify` checks four things:

## 2. Experiment matrix (`configs/formal/exp_matrix_v1.json`)

The independent unit is an **episode**: one commanded scenario on one device in one run. Windows inside an episode are not independent repetitions.

| Component | Runs | Mode | Content |
| --- | --- | --- | --- |
| Detection | exp-s01 to s25 | shadow (no policy change) | In every session each of the ten devices runs a different behavioural anomaly; kind index = (device index + session index) mod 5. **5 repetitions per anomaly type per device: 250 episodes.** |
| Silence and context | exp-s26 to s30 | shadow | One silence episode and one operating-time withdrawal, on two different devices per session, rotated over all ten devices: 5 silence and 5 context episodes |
| Benign | exp-s31 to s35 | shadow | No commanded scenario |
| Enforcement | exp-a01 to a12 | active-authorized, **device02 only** | 25 behavioural episodes (5 per type), 5 context episodes, 5 identity episodes |
| Reserved TEST | g6c-d07, g5d3a-fx-g6b09, g5d3a-fx-g6b17 | offline | Scored once by the frozen release |

**Anomaly parameters** (catalogue defaults, fixed for every episode):

| Type | Parameter |
| --- | --- |
| rate | factor 5 |
| payload | 1024 bytes |
| burst | group 5 |
| jitter | fraction 0.8 |
| drop | probability 0.8 |

**Timing.**

| Episode | Onset | Duration |
| --- | --- | --- |
| Behavioural, devices with 10 s or 20 s windows | 150 s | 120 s (10 s windows) or 160 s (20 s windows) |
| Behavioural, devices with 90 s or 180 s windows | 180 s | 270 s (90 s windows) or 360 s (180 s windows) |
| Silence | 150 s | 200 s (360 s for device08), always longer than its liveness bound |
| Context withdrawal (shadow) | 300 s | — |

Behavioural episodes are at least two native windows long. On the active device02 block:
- a behavioural episode runs until a verified containment, or for at most 110 s, after which it counts as **censored**;
- the context withdrawal comes at 480 s;
- an identity episode starts no earlier than 400 s.

**Change from the draft protocol.**
- **What changed:** identity episodes run only in the supervised device02 sessions.
- **Why:** an identity episode is a declared revocation at the broker, which is itself a policy change, so it cannot run in a shadow session.
- **What stayed the same:** the other nine devices are evaluated for detection, trust state and decision latency as planned.

**Seeds.** Each run has a fresh run id. Its plan and seeds are generated by the frozen `core_final_plans.py --retest RUN` from that run id.

## 3. Run rules (declared before the data)

- **VALID:** every check of `exp_validity.py` holds.
- **VOID:** only for machine-checked infrastructure causes, never for results:
  - a failed verification or clock certificate;
  - a launcher, workload or observer failure;
  - a failed binding audit;
  - an unapplied scenario command;
  - in an active run, a cancelled owner instruction or abandoned episodes.

  A VOID run is kept and reported, and replaced once by its spare:
  - exp-s36 to s40 replace detection or benign runs;
  - exp-s41 to s45 replace exp-s26 to s30 one to one;
  - exp-a13 replaces an active session that has a context episode, and exp-a14 any other active session.
- **STOP:** the campaign stops on any of:
  - enforcement in a shadow run;
  - a broker policy other than the baseline digest during or after a run;
  - a PEP outcome outside device02 or a failed outcome;
  - a restoration failure;
  - a changed protected fingerprint;
  - an unclean tree;
  - a failed verification;
  - a second consecutive VOID with the same failed checks.

  A STOP needs a person's review before anything else runs.

## 4. Aggregation rules (declared before the data)

The definitions are those of the frozen `exp_metrics.py`. `exp_aggregate.py` regroups its per-window construction and must reproduce, for every run, the frozen tool's window counts and its flag-level and decision-level confusion counts. Any mismatch is reported.

- **Detection** (FPR, FNR, precision, recall, F1, per device, per anomaly type, and episode detection delay) uses the **shadow** runs, where all ten devices run under identical conditions.
- **Trust-state accuracy** keeps the windows of a device whose operating time was withdrawn, after the declared cut, as **context windows** (expected RESTRICT). They are kept separate from the behavioural POSITIVE and NEGATIVE windows. Behavioural, context and overall agreement are all reported.
- **Time-to-Contain and enforcement success** use the **active** device02 runs. Time-to-Contain is split into observation, PDP, operator-authorization and enforcement time. Censored episodes are kept, and automatic and reviewed containments are reported separately.
- **PDP decision latency** uses every VALID run, per device: median, p95, maximum, and p99 where n ≥ 100.
- **Silence:** the delay from onset to the first liveness recommendation.
- **Context:** the delay from the cut to the first context recommendation, and whether it escalated to QUARANTINE.
- **Identity:** the delay from revocation to the review and to the verified QUARANTINE.
- **Reserved TEST:** reported separately as held-out benign evidence (false flags, false non-FULL decisions, trust-state agreement, T distribution, per device).

## 6. Not changed, not claimed

- The trust parameters (α 0.2, β 0.5, γ 0.3, λ 0.1, τ_Q 65, τ_R 75, N = 2) are development-stage choices, disclosed as such.
- Automatic enforcement is claimed for device02 only.
- Calibration is fragile on devices 05, 07 and 08, and devices 08 and 09 use long windows.
- MQTT quarantine is application-level, not network isolation.
- Scaling beyond ten devices is future work.
